This page is the release truth table. Source code, local tests, deployed state,
and authenticated browser/API canaries are separate proof lanes.

## Live: production partner-preview baseline

For admitted **personal tenants**:

- `praxa_sk_` tenant API keys and the edge/authentication boundary;
- strict minimal `POST /v1/execute` with `mode:"task"`;
- `GET /v1/runs/{run_id}`;
- resumable `GET /v1/runs/{run_id}/events` SSE;
- cooperative `POST /v1/runs/{run_id}/cancel` requests;
- tenant-scoped `GET /v1/usage` backed by completed provider-call and settled
  retail evidence;
- automatic forward projection of the eight strict task webhook event types;
- bearer webhook endpoint management and delivery readback;
- HMAC-SHA-256 signed webhook delivery with one-time endpoint secrets;
- signed-in personal key and usage management for the admitted cohort.

Every admitted task still passes fail-closed funding reservation and settlement
authority. Usage readback is evidence, not invoice or reservation authority.

## Deployed, pending separate production canaries

The following refinements remain closed until their own production canaries
prove the exact behavior described here.

### Exact browser-action approvals

- customer-safe `pendingApproval`, `approval.required`, and
  `approval.resolved` for immutable `browse_session_act` input only;
- exact instruction/steps plus target host;
- 64-character digest binding;
- public mutation decision `approve` or `deny`;
- fail-closed suppression and refusal for every unsupported or unverifiable
  approval.

This is not generic tool approval or a unified configurable policy engine.

## Source-ready, not production-activated

The following work exists in the source tree and has repository-level contract
coverage. None of these entries is a live claim. Each still needs the activation
evidence named below.

### Portal-native personal build surfaces

- personal agent list, create, detail, edit, preview, chat, analytics, and
  conversation routes rehost the existing custom-agent system under
  `/developers/build/agents`;
- personal workflow list, create, detail, and edit routes rehost the existing
  automation system under `/developers/build/workflows`; and
- the playground selects a personal agent and opens its server-owned draft in
  the real metered preview runtime without retaining an API-key secret or
  accepting a client-supplied model override.

Activation requires a compatible Worker deployment and an authenticated browser
canary across create, edit, preview, navigation, metering, and permission-refusal
states. The rehosted workflow UI is not the public typed workflow DSL.

### Portal-native account, organization, and billing views

- profile name, nickname, private preferences, avatar upload, provider/email
  facts, and sign-out reuse the existing account authorities;
- organization list/create, member directory, add-existing-username,
  member/admin role changes, and member removal reuse existing organization
  authority; and
- subscription status and credit display reuse existing usage/subscription
  evidence, while eligible free or terminal users can start an allowlisted
  Stripe Checkout.

The checkout server guard refuses a new subscription flow for `active`,
`in_grace`, or `in_retry` evidence and fails closed when subscription state
cannot be proven. There is no developer-portal Stripe Customer Portal,
payment-method editor, cross-provider cancellation flow, organization key, or
organization execution authority.

Activation requires a compatible Worker deployment plus authenticated profile,
avatar, membership/RBAC refusal, subscription-state, trusted-redirect, and
duplicate-subscription billing canaries.

### Agent evaluation datasets

The source-ready dataset slice provides personal and organization-scoped
datasets, mutable current items, resumable server-validated JSONL ingest,
immutable published revisions/items, revision-addressable exports, and
canonical SHA-256 evidence. Ordered chunk receipts, stale-revision checks,
atomic finalize/abort behavior, bounded retention, authenticated routes,
row-level security, and database mutation functions exist in source.

The migration is not recorded as applied here. Activation requires migration
review/application, a compatible Worker deployment, scheduled ingest cleanup,
and production canaries for AAL2, authorized management, two-organization
refusal, interrupted/replayed ingest, digest binding, and published
immutability. Publishing a dataset does not execute an experiment.

### Governed workflow and experiment authorities

The source tree now contains two separate platform authorities:

- workflow create, update, pause, resume, complete, archive, run, and cancel
  commands with AAL2, tenant-derived authorization, idempotent receipts,
  optimistic stale-state checks, immutable run ownership, and point-of-use
  revocation; and
- experiment execution that freezes dataset, configuration, evaluator, runtime,
  agent, and billing identities; reserves a bounded aggregate credit ceiling;
  dispatches durable shards; and records customer-safe result and comparison
  receipts with cancel/resume generation fencing.

These are source-ready backend boundaries, not customer availability claims.
Their migrations are not recorded as applied, the Worker release is pending,
and authenticated two-tenant, billing, capacity-race, cancellation, redaction,
and browser canaries have not been completed. The portal therefore keeps
workflow mutation and experiment execution controls unavailable.

### Redacted causal-trace authority

A source-ready trace projection records value-free span lineage, phase,
actor kind, argument key names, digests, safe retail credits, and retention
metadata. It deliberately excludes prompts, outputs, credentials, provider
cost, and infrastructure cost. Migration, retention deployment, permission
proof, and an authenticated redaction canary remain pending, so the live portal
continues to expose only its narrower projection timeline.

### Typed workflow DSL foundation

Strict plan schemas, canonical compilation, serialization, interpreter behavior,
and Cloudflare step-adapter contracts exist in source. The foundation remains
gated: there is no public route, SDK package, deployed customer-definition
authority, or connection to `/v1/execute`. Customer activation still requires
tenant/version authority, billing, approvals, cancellation, suspension/resume,
projection, migration, deployment, and production proof as one boundary.

## Live cancellation reconciliation behavior

The reviewed migration is applied, the compatible Worker fleet is deployed,
and separate production canaries observed both cancellation branches. A
claimed model-backed run cancelled before provider mutation finished public
`cancelled`, released its complete reservation, charged zero credits, emitted
one terminal `run.cancelled`, and resumed SSE only after the requested cursor.

A provider-in-flight cancellation retained one run, task, claim, executor, and
process under idempotent resubmission. While internal state was
`reconcile_required`, its public run stayed `running` and non-terminal and its
stream emitted this exact warning:

```text
The run is reconciling an uncertain execution outcome. Do not retry or resubmit it.
```

The scheduled reconciliation owner later settled the frozen billing ceiling
once and converted the unverifiable committing outcome to `run.failed` with
`code: "run_outcome_unknown"`, message
`A committing action may have happened, but the final outcome could not be verified. Do not retry automatically.`,
and `retryable: false`. The resumed stream ended with one byte-identical
`run.failed`; the run never became publicly cancelled or retryable. These are
bounded canary observations, not a promise that every provider exposes a
recoverable cancellation receipt.

## Live canonical developer portal host

The intended origin is `https://platform.praxa.io/developers`, with consumer
destinations on `https://app.praxa.io` and API traffic on
`https://api.praxa.io`. The deployed portal accepts email-link/OTP fragment
callbacks, clears the callback credentials from the URL, persists the resulting
browser session, and requires durable legal acceptance before developer routes
render. This release does not add provider-button sign-in or an account-recovery
flow. A production browser canary proved callback credentials were removed from
the URL, the authenticated session survived reload, legal acceptance persisted,
and `/`, `/developer`, and `/developers` all retained the platform origin.
Read-only HTTP checks separately proved `200` responses for nested API-key,
run, webhook, and usage routes and an exact `app.praxa.io` developer deep-link
redirect back to the matching platform route.

## Unavailable

- `mode:"turn"` and the rich turn event stream;
- request-level `agent`, `context`, `tools`, `policy`, or `delivery` overrides;
- organization execution and organization API keys;
- configurable unified policy packs;
- generic tool approvals and mature approval receipts;
- published npm SDK;
- BYO provider credentials;
- customer experiment execution and model comparison;
- a public typed-workflow definition or execution route;
- developer-portal subscription cancellation, payment-method changes, and
  Stripe Customer Portal sessions;
- mature hash-chained receipts/evidence export;
- dedicated/self-hosted deployment and enterprise governance surfaces.

## Remaining preview gates

1. Deploy and browser-canary the source-ready portal agent, workflow,
   playground, profile/avatar, organization, and billing surfaces.
2. Review/apply the additive dataset, workflow, experiment, and trace
   migrations; deploy the matching Worker routes; then prove authorization,
   cross-tenant refusal, receipt binding, billing/capacity races, redaction,
   and immutable revision behavior in production.
3. Prove exact browser-action approval, including stale, mismatched,
   unsupported, and cross-tenant refusal.
4. Exercise retry, dead-letter, and eligible replay behavior against live
   webhook destinations before claiming those operational canaries complete.

General availability additionally requires external-client load, rollback,
support, SDK publication, and security proof. Existing custom-agent deployment
credentials remain a separate supported surface.
