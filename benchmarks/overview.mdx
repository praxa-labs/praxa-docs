Praxa publishes evidence by lane so you can distinguish implementation checks
from agent performance and production behavior. The public
[`praxa-benchmarks`](https://github.com/praxa-labs/praxa-benchmarks)
repository contains reviewed, redacted methods and publication artifacts.

## Evidence available today

The preprint [_From Proposal to Verified Effect: Praxa, an Evidence-Bound
Harness for Governed AI Agent
Execution_](https://github.com/praxa-labs/praxa-benchmarks/releases/tag/preprint-v1.1.0)
reports two distinct empirical lanes.

### Repository-local harness validation

Repository-local validation checks whether the implementation satisfies its
own executable contracts. The reported source revision passed 1,027 unit tests
and 89 Workerd runtime tests. The instrumented source inventory covered all 363
expected files. Measured statement, branch, function, and line coverage were
68.09%, 62.31%, 75.09%, and 70.84%, respectively.

These checks support scoped claims about regression behavior, route and schema
contracts, packaging, and fail-closed gates at the tested revision. They do not
measure general agent intelligence, task success on unseen work, production
latency, or verified external effects.

### Terminal-Bench pilot

A formative Terminal-Bench Core 0.1.1 study compared a baseline agent loop
with a reliability-oriented loop. The study used one model, 12 curated tasks,
and three attempts per task in each arm, for 36 trials per arm. Both arms used
the same model, base prompt, step limit, wall-clock limit, and token budget.

| Metric         |  Baseline | Reliability-oriented |            Difference |
| -------------- | --------: | -------------------: | --------------------: |
| Trial accuracy |     47.2% |                47.2% | 0.0 percentage points |
| Input tokens   | 1,624,737 |            2,233,805 |                +37.5% |
| Output tokens  |    34,122 |               51,431 |                +50.7% |

The aggregate trial-accuracy result is a tie with higher token use in the
reliability-oriented arm. Individual tasks moved in both directions. Pass-at-k
is intentionally omitted because the aggregate summary and one arm's raw
metadata disagreed. The pilot therefore supports analysis of failure modes and
harness tradeoffs, not a claim of improved accuracy or cost efficiency.

## Evidence classification

Use the evidence class attached to a result before you rely on it.

| Evidence class                | What it can support                                                          | What it cannot support                                                      |
| ----------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Repository-local validation   | Tested implementation and contract behavior at an identified source revision | Live provider behavior, production reliability, or general task performance |
| Controlled benchmark pilot    | Results for the stated task sample, model, prompts, budgets, and attempts    | Broad generalization, causal superiority, or deployment readiness           |
| Synthetic conformance fixture | Benchmark-runner and gate mechanics                                          | Model quality, provider performance, or production outcomes                 |
| Protected provider run        | Provider-backed behavior under a recorded experimental setup                 | Production behavior unless the production environment was observed          |
| Production observation        | Behavior in the identified deployment and observation window                 | Universal behavior outside that deployment and window                       |

The current publication reports the first two classes. It also documents
synthetic conformance fixtures only as protocol checks. A fixture that contains
constructed outcomes is not a provider benchmark.

## Results that remain unpublished

Praxa has not published measurements for these production-sensitive questions:

- End-to-end mission latency against a deployed Integration Gateway
- SSE throughput or tail latency under controlled load
- Provider-effect success confirmed by an independent verifier
- Reliability across multiple model families and repeated task samples
- Comparative cost, latency, or accuracy against another harness
- Longitudinal behavior in a production deployment

These results require controlled credentials, fixed bindings and budgets,
redacted evidence, and independent review. A planned run or a passing local
gate does not substitute for the run itself.

## How to interpret future results

Before comparing a Praxa benchmark, confirm that the artifact identifies:

1. The source revision and package versions
2. The model, provider, reasoning settings, and prompt bindings
3. The task suite, sampling method, and number of attempts
4. The resource budgets, time limits, and stopping conditions
5. The metric definitions and aggregation method
6. The execution environment and evidence class
7. Missing trials, failures, exclusions, and limitations

Compare results only when these conditions are compatible. Treat latency and
throughput as deployment-specific measurements, not SDK constants.
